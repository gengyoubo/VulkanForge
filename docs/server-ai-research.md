# 服务端 AI 与寻路：第一轮研究

用户给出的研究顺序从实体 AI 与寻路开始，其次是实体碰撞候选查询。本轮只做热点识别和实验设计，不改变游戏行为。

## 已有采样

同一个“测试”单人存档的 90 秒 JFR 窗口，服务端线程共记录 1418 个 Java 执行样本；统计的是包含指定类别方法的调用栈，一个样本可属于多个类别。本节和下文 JFR 窗口的样本数已按完整栈重算（初版因 `jfr print` 默认只输出栈顶 5 帧而漏计）；密集场景段落中的 68 / 100 个样本窗口未能对应到保存的结果文件，未重算：

| 栈帧类别 | 样本数 | 占服务端线程样本 |
| --- | ---: | ---: |
| 原版路径计算 / 导航包 | 15 | 1.06% |
| 原版 Goal 包 | 99 | 6.98% |
| 原版 Brain / behavior 包 | 0 | 0% |
| 实体区段查询 | 39 | 2.75% |
| `BlockCollisions` | 20 | 1.41% |

这只是当时的位置和操作，不能推断实体密集、村民大厅或大型模组工厂的情况。JFR 数字不是精确 Tick 时间；方法内联、有限栈深、原生代码以及不在这些包名中的模组 AI 可能漏计。零样本不代表没有开销。`EntitySection` 查询也服务于其他用途，不能把它们全部当成碰撞；类别有交集，不能把占比相加。

对照之前的 Radium 开发测试：160 头牛的 25 秒合成场景记录 154 个服务端线程样本，其中路径/导航包 11 个、实体区段查询 22 个、方块碰撞迭代器 21 个。其世界、优化模组、实体和采样数都与真实存档不同，不能用来计算两场景性能差或证明牛群代表玩家负载，但说明压力场景中这些路径可以变得更显眼。

真实实例包含 Canary 0.3.3。检查用户安装的 JAR，发现其包含寻路节点、导航区域、目标集合和 Brain 等相关的 Mixin 类；类存在不等于每个补丁在本实例都实际启用或作用于具体热点。后续选补丁时应先确认实际配置与变换，避免重复或冲突。此前采样中 MFCL 的物品转换回调仍比这些已识别的 AI 栈帧更显眼；不要因为列表排名而把当前存档的实际热点排除。

## 下一步实验

1. 在隔离世界副本建立固定负载：普通游荡动物、需要绕障碍寻路的生物、村民与 POI、模组实体各一组。记录物种、数量、目标、地形、玩家位置、区块加载状态和随机种子。为目标移动或方块变化单设场景；不要将不同任务混成一个结果。
2. 每组以同版本 Canary + VulkanForge 为基线，分离预热和采样，记录 MSPT 的分布、服务端 CPU/GC、实体实际 Tick 数，以及寻路请求次数、完成/失败、距离和每次访问节点数。先用低侵入 JFR 找到具体调用链，再用有开关的计时器测开销，并对比计时器关闭组。测试器本身不得修改实际世界或直接在工作线程读取游戏对象。
3. 若真实或可复现场景证明路径计算足够重，再选定一个原版或明确支持的实体类型，研究数据结构或重复计算；未知模组行为一律保留原路径。异步寻路只作后续候选，需完整快照、结果失效校验、限队列和回退，还必须测 AI 决策延迟及行为差异。
4. 分别测试实体区段查询，固定密度、玩家分布和移动行为，检查缓存失效、跨区块/维度和查询结果顺序；先核对 Canary 已覆盖的范围。不要为提升指标跳过实体、降低 Tick 频率或改变寻路结果。

退出标准：没有稳定的端到端瓶颈或新增收益时，不合入补丁。若某个候选能复现收益，再做行为差分与长时间测试；广泛的第三方模组兼容留待之后单独验证。

## 2026-11-06：动物游荡与绕障场景

新增开发用 `AiWorkload` 与 `tools/benchmark-server-ai.py`。脚本从已停服的测试模板各复制一份世界，核对哈希后在每个副本里建造 16×16 的隔离场地；工作负载要求目录中存在脚本创建的专用标记，不能直接在未标记世界启用。两个场景各生成 32 头牛并固定其随机源种子：

- `wander` 让牛自然游荡，记录导航路径对象的变化。
- `obstacles` 在场地中建立有缺口的墙，按实体分散调度，每 80 Tick 显式请求墙两侧交替的目的地。

固定随机源不保证 Minecraft 世界和实体调度完全确定。原始场地可能受到初始世界、自然刷新和运行时随机状态影响。本轮是单次可复现流程检查，不是多轮性能对比。路径对象变化数是观察到的安装数，不是总请求数；显式请求数也不等于实际搜索次数（导航可能复用路径）。`reachable` 是返回路径的 `canReach()` 标志，不证明实体已经到达目的地；`pathNodes` 是返回路径节点数的总和，不是搜索过程中扩展的节点数。

环境为 Forge 47.4.28、Java 17、VulkanForge 和 Canary 0.3.3，Canary 原始 JAR 的 SHA-1 与用户实例一致；未加载完整整合包，且 Forge 小版本与用户的 47.4.23 不同。每组预热 200、采样 600 Tick，JFR 开启。计数覆盖预热与采样共 800 Tick；Tick CSV 仅覆盖采样期。服务器线程事件之间的耗时不包含整个主循环，不能直接当作完整 MSPT。

| 场景 | 牛 Tick | 显式请求 | 非空 / 标记可达 | 路径对象安装 | 采样区间平均 / P95 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 游荡 | 25600 | 不统计 | 不统计 | 104 | 3.52 / 6.72 ms |
| 绕障 | 25600 | 320 | 318 / 285 | 385 | 3.10 / 5.93 ms |

两个负载行为不同、仅一轮，不应把均值相减当成寻路成本或用于证明某组更快。各取采样期内 25 秒 JFR，游荡 / 绕障分别得到 89 / 78 个服务端线程样本；路径/导航类分别出现 5 / 3 个样本，方块碰撞分别出现 1 / 9 个样本。数量很少，JIT 内联和缺失栈会进一步影响解释，无法据此确定热点排序。

数据与场景日志：`build/reports/server-ai/9ee581f6-6c50-4771-a054-5ad5c0a0fd0a/`，其中 `manifest.json` 保存了输入世界和 Canary 的哈希。较短的检查运行也验证了两个场景和停服；一次早期运行因本地文件依赖未正确重映射 Canary 而失败，现已改为固定的 Curse Maven 文件 5089991，并确认下载的原始 JAR 与实例 SHA-1 一致。该失败没有产生有效性能数据。

复现（需要 Java 17、已同意 EULA 且已停服的 `run-server-baseline` 测试模板）：

```powershell
python tools/benchmark-server-ai.py --canary '<实例中的 Canary 0.3.3.jar 路径>'
```

脚本会拒绝散列不匹配的 Canary 和不完整采样，并在 `build/reports/server-ai/` 创建新的隔离目录，不覆盖模板或用户存档。上述初次运行本身不能用于选出可合入的优化；后续扩展见下文。

## 2026-11-06：村民、模组实体和搜索计数

继续扩展隔离场景：`villager_poi` 在围栏内放置床与工作站并生成 8 名村民；`changed_wolf` 使用用户实例的 Changed 0.15.7 中 8 只雄性深色胶狼和带缺口的墙。Changed 的下载工件与用户安装 JAR 的 SHA-256 相同；场景只加载 VulkanForge、Canary 和 Changed，**不是完整整合包**。实体通过注册表直接创建，不能保证等同于自然生成的全部初始化和玩家活动。

`--count-nodes` 只在开发测试时插桩服务端线程的 `PathFinder.findPath`：统计调用、正常返回次数、调用墙钟时长、最长时长及内部 `BinaryHeap.pop` 次数和单次最大值。堆取出次数是搜索循环中实际弹出节点数，不能与最终路径长度、生成节点总数或请求总数混同。计数覆盖预热与测量 800 Tick、场景里服务端线程的全部此类调用，可能包含其他实体；它不包含绕过 `PathFinder` 的模组自定义算法。纳秒计时包含调度、GC、计数及其他插桩开销；抛出异常不会计入正常完成，脚本会拒绝完成数不一致的结果。

固定 200 Tick 预热、600 Tick 采样，JFR 开启，单次 Changed 插桩运行验证 6400 次实体 Tick、80 次显式导航请求和 76 条标记可达的非空路径；`PathFinder` 实际进入并正常返回 106 次、堆弹出 2852 次，累计墙钟约 68.1 ms。该累计含预热，不可直接除以 600 与采样期 Tick 均值比较。一次未插桩对照也完成了 6400 次实体 Tick，结果保存于独立目录；两次运行不足以测量插桩开销或证明性能差异。

村民场景做了两轮交替顺序的开关对照：每组都验证 6400 次实体 Tick，8 名村民在运行中都曾获得家和工作站记忆。第一轮无插桩 / 有插桩的事件间 Tick 均值分别为 4.49 / 4.06 ms，第二轮为 4.13 / 4.21 ms；P95 分别为 8.43 / 7.60 ms 和 8.21 / 8.65 ms。两次插桩分别记录 69 / 89 次正常搜索、3245 / 2912 次堆弹出、约 74.1 / 87.9 ms 累计搜索墙钟。村民决策与路径数有随机波动，这两轮不能给出可靠的插桩开销，也不能证明优化收益。

计数器和两场景属于 smoke 代码；普通资源输出已检查不包含计数用 coremod 或计数类。实验数据：村民交替运行 `build/reports/server-ai/85581742-42cb-47c9-b77d-debb5aa4f686/`；Changed 插桩 `build/reports/server-ai/fa277c5f-5a4c-4a2f-81f4-f7556204a20d/`、无插桩 `build/reports/server-ai/14550d93-a95f-4ff5-959d-d27eccfb7cf7/`。当前仍未按 Tick 分桶搜索耗时，也未获得其他模组与真实玩家场景的精确路径开销；不能将这些人工场景结果推断为实际服务器的 Tick 占比。

可用 `--scenario villager_poi --compare-instrumentation --rounds 2` 交替运行开关对照；Changed 场景使用 `--scenario changed_wolf --changed-jar '<实例中的 Changed 0.15.7.jar 路径>'`，加 `--count-nodes` 才启用计数。默认 `--scenario all` 覆盖游荡、绕障和村民，Changed 为单独可选场景。

## 2026-11-06：按 Tick 分桶和密集场景

开发采样器现在同时记录每个服务端 Tick START/END 事件之间的 `PathFinder.findPath` 调用数、正常返回数、堆节点弹出数和墙钟时间。使用顶层调用时间，避免重入时把嵌套时间重复相加；若调用跨越测量边界、异常未返回或计数不一致，分析脚本拒绝该数据。时钟包括插桩、线程调度、GC 和搜索内部调用，且仅覆盖服务端线程中经过该原版 `PathFinder` 的同步搜索。事件边界不等于 Minecraft 完整 Tick，其他监听器的事件开销、异步线程和模组自定义搜索可能不被计入。CSV 同时标记是否开启插桩；`tools/analyze-ai-ticks.py` 拒绝把关闭插桩的零值当作搜索统计。

在同一模板副本上新增 `villager_dense`（16 名村民、16 床、16 工作站）和 `changed_dense`（32 只 Changed 深色胶狼、固定障碍和交错发出的导航请求）。每组预热 200、测量 600 Tick；所有组均启用 JFR。两轮交替顺序的插桩组结果如下：

| 场景 / 轮次 | 搜索 Tick / 600 | 搜索总墙钟 / 600 Tick | 搜索 / 事件间墙钟 | 最慢 5% Tick 中有搜索 | 最慢 5% Tick 的搜索墙钟占比 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 16 村民 / 1 | 46 | 65.28 ms | 2.39% | 11 / 30 | 12.29% |
| 16 村民 / 2 | 67 | 59.27 ms | 2.19% | 9 / 30 | 5.17% |
| 32 胶狼 / 1 | 267 | 99.15 ms | 3.33% | 18 / 30 | 5.78% |
| 32 胶狼 / 2 | 267 | 106.83 ms | 3.16% | 19 / 30 | 4.21% |

慢 Tick 比例是同一组最慢 30 个事件间隔里搜索墙钟的合计 / 这些间隔的合计；存在搜索不证明它造成慢 Tick。村民两组中最大的单 Tick 搜索墙钟约 7.39 / 7.15 ms，偶发峰值值得后续跟踪；胶狼两组约 5.44 / 3.03 ms。每组均验证实体 Tick 计数、导航活动与正常存档；村民运行中 16 名都曾获得家和工作站记忆。胶狼场景每组显式请求 320 次，其中 313 条返回路径标记可达，**不代表已经抵达**。

开关对照的事件间平均值：村民无插桩 / 有插桩分别为 4.56 / 4.55 ms、4.30 / 4.50 ms；胶狼为 4.66 / 4.97 ms、5.79 / 5.64 ms。顺序交替，但只有两轮且村民行为有波动，不能据此精确扣除插桩成本。JFR 每场景各取一个 25 秒窗口，仅 68 / 100 个服务端线程样本，区块调度、卸载/保存和方块实体 Tick 栈也有出现；样本不足以可靠排名。

这些数据说明寻路在这两个受控场景中的**总量相对有限，但可能参与个别慢 Tick**；不构成真实服务器排名或优化收益证明。下一步若继续研究 AI，应针对单次慢搜索重现其起点、终点、地形和扩展节点，再比较同样场景下区块、方块实体及查询热点；不要仅依据最慢 Tick 与搜索同时出现就改写 AI。

数据与逐 Tick CSV：`build/reports/server-ai/8177cf03-6259-4f21-8ecd-e8a9354781bd/` 和 `build/reports/server-ai/8f76acff-15f3-442d-96f9-cbd4b9bbbcbe/`。用 `python tools/analyze-ai-ticks.py <CSV> --expected-samples 600` 可重新计算；场景通过 `--scenario villager_dense` / `--scenario changed_dense --changed-jar <路径>` 和 `--compare-instrumentation --rounds 2` 运行。仍未实现真实玩家服务器上的逐 Tick 插桩，也未完成自定义寻路实现或高负载真实性验证。
