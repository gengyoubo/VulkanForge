# 区块保存、分配与跨模组传输：Java 模拟

## 区块 NBT 和写入

Forge 1.20.1 的 `ChunkSerializer.write` 构造区块 NBT，其中包含每个方块实体的保存数据；区域文件默认使用 DEFLATE 包装输出流。本实验调用真实 Minecraft `CompoundTag` 和 `NbtIo.write`，构造 0、64、512 个**合成**方块实体，每个有位置、能量、进度、256 字节负载和单物品库存，再对比：

1. 先把 NBT 编码到完整字节数组，再 DEFLATE；
2. NBT 直接经缓冲输出流写入 DEFLATE。

每组都比较压缩字节，解压并按 NBT 读回，结果相同。三个独立 JVM，各预热 70 对、交替测量 200 对；下表是三个进程各自中位值的中位数。每次都包含构造合成 NBT；分阶段编码与压缩的中位值不能简单相加得到总时间的中位值。

| 方块实体数 | 分阶段总时间 | 流式总时间 | 分阶段线程堆分配 | 流式线程堆分配 |
| ---: | ---: | ---: | ---: | ---: |
| 0 | 0.0107 ms | 0.0125 ms | 2,056 B | 9,904 B |
| 64 | 0.269 ms | 0.249 ms | 225,800 B | 122,608 B |
| 512 | 1.662 ms | 1.552 ms | 1,507,096 B | 625,232 B |

512 个实体的分阶段测试中，构造 NBT 中位约 0.063 ms，编码约 0.489 ms，压缩约 1.012 ms；流式的编码与压缩交织，不能拆出同样的两列。流式模式在无实体时有缓冲区固定成本，在本合成高密度场景减少了中间数组分配。**原版区域文件已使用流式压缩，不能把这个对照当作对原版的优化。**线程分配计数不包含其他线程和原生内存。

另将合成压缩结果写入开发目录下的临时文件；同一个打开的文件重复覆盖 30 次，分别测量 `write` 和 `force(false)` 的墙钟时间，然后删除该临时文件。三个进程各场景的写入中位约 0.052–0.093 ms，强制刷写中位约 0.211–0.488 ms；某一次场景的 30 次样本中 `force` P95 达 6.04 ms。文件系统缓存、操作系统调度及设备配置都会影响结果，强制刷写频率也不代表游戏真实保存行为。

这是简化数据：没有真实的 `ChunkSerializer.write` 调用、区块节/光照/结构、真实 Mekanism 机器 NBT、区块调度、区域文件头或并发服务端；合成字节负载在 32 种内容间重复，可压缩性不等同于用户存档。压缩和 I/O 测试均不能推算真实 MSPT 或长 Tick 的原因。

## 旧生存录制中的线索

对 MFCL 优化前的 120 秒生存 JFR 作完整栈统计：服务端线程 2,750 个 Java CPU 样本中，10 个包含 `ChunkSerializer`、238 个包含某种 NBT 类；后者包含其他功能和模组，不能当作区块保存占比。服务端线程有 4,838 个对象分配**采样事件**，其中 64 个栈含 `ChunkSerializer`；采样次数不是分配字节数，不能当作完整对象计数。该录制未启用 `DebugNonSafepoints`，结果也不代表 MFCL 优化后的表现。

录制的阈值过滤文件事件中，50 个区域文件 `.mca`/`.mcc` 写入发生在线程名不是 `Server thread` 的线程，事件时长总和约 5,054 ms、最长约 232 ms；另有 4 个此类区域文件读取事件。这些是单次 I/O 调用的墙钟事件，可能包含重叠、系统调度和等待，不能简单相加成主线程等待时间，也不能证明物理磁盘耗时；低于录制阈值的事件不在统计中。录制中还有 44 个 `GCPhasePause` 事件，总时长约 5,969 ms、最长约 2,596 ms；尚未与 Tick 时间线和 GC 原因对齐，不能据此归因长 Tick。

## 跨模组传输与反射模型

同一旧录制中，有 9 个服务端 CPU 样本同时包含 Mekanism `EnergyNetwork.tickEmit`、Forge 能源适配和 AE2 能量注入栈；`EnergyCardRuntime.getInstalledEnergyCards` 共有 10 / 2,750 个服务端样本。样本重叠，数量很小；它们提供调查线索，不说明这些调用重复，也不是 Tick 时间比例。Create 的传输方法没有被当前启发式匹配到，并不证明它没有传输开销。

对实例中的 `ae2_overclocked-1.2.3-fix3` jar 做只读字节码检查，发现其能量卡后备路径使用 `Class.getMethod`、`getDeclaredField` 和反射调用查找升级及宿主，递归深度上限为 4；所检查的 AE2 基类 `getBlockEntity()` 返回自身。实际运行时对象、Mixin 和模组状态可能改变具体路径，不能仅靠静态字节码断定每次都走同一分支。

第二个 Java 模型只模拟宿主成员发现：比较每次反射查找与按类缓存**反射元数据**，每次仍调用方法、读取对象字段，不缓存卡的数量、机器状态或调用结果。测试缺失方法、动态公共宿主、私有字段、继承的私有字段、抛异常方法和自引用；动态状态比较及自引用五次 `getBlockEntity` 调用数量一致。模型不包括真实 AE2 接口、配置检查、完整升级库存和所有递归分支。对不存在成员只缓存 `NoSuchMethodException`/`NoSuchFieldException`，其他查找失败不永久缓存；实际类重定义、安全上下文、模组热加载及方法调用副作用仍需验证。

三个独立 JVM 的微基准只证明这种机制值得追踪：缺失成员和自引用场景缓存后明显减少重复反射异常与分配，但 JIT 可内联和消除对象，模拟是单态假对象，数字不可外推到用户服务器。下一步应对当前 MFCL 版本的实例副本计数调用频率、对象类型与缓存命中，并比较实际方法执行时间和分配，再决定是否在 AE2 超频自身实现可选补丁；不能据此直接添加通用 Capability 缓存。

## 文件与复现

- `python tools/benchmark-chunk-save-simulation.py --forks 3`：合成 NBT；需要 JDK 17 和项目 Gradle 缓存。结果在 `build/reports/chunk-save-simulation/d092f492-fad6-4721-aa93-dbfd1005cd08/`。
- `python tools/benchmark-transfer-reflection-simulation.py --forks 3`：反射宿主发现模型。
- `python tools/analyze-chunk-storage-jfr.py <录制.jfr>`、`python tools/analyze-chunk-file-events.py <录制.jfr>`、`python tools/analyze-crossmod-transfer-jfr.py <录制.jfr>`：只输出聚合信息，不输出 JFR 文件路径字段或 JVM 启动参数。

原始生存 JFR 保存了启动参数等敏感信息，不应外传；本次没有读写原始世界或部署修改。
