# Mekanism 接收端拓扑展开：Java 模拟

## 测试内容

候选方法将位置→方向的嵌套接收端结构展开成列表，并缓存列表；连接变更使其失效。候选仍逐面检查端点有效性、做首次模拟插入，并按原先顺序调用分配方法；没有缓存可插入数量，也没有跨面去重。模型使用 Java `LinkedHashMap` 和模拟端点；分配使用 Mekanism 50978fc 的 `Target`、`SplitInfo` 和 `IntegerSplitInfo` 原始源码。它不是 Forge/Mekanism 运行环境，不能用结果代替游戏性能。

三个独立 JVM 各跑了 10,000 次有固定随机种子的行为对照，比较每次的模拟调用、执行调用、发送量和存储最终数量。场景包括两个面共享一个存储、端点增删、启停、失效、容量和存量变化、清空与重建。三次均通过。所有变化发生在两次 Tick 之间；没有验证实际 `LazyOptional`、网络合并拆分的原生实现、Tick 内重入、跨区块卸载、外部模组副作用或线程行为，也没有逐步验证真实机器和存档。这个结果仅证明模型覆盖的行为一致。

## 计时

每个独立 JVM 预热 4 对，再交替运行 6 对；表中为 18 组结果各自的中位数。单次是模型内一次发送，包含重置模拟存储、筛选、模拟与分配，不是服务器 Tick 耗时。`每 32 次`和`每次`表示人为将候选缓存标记为失效的频率，并不代表真实服务器频率；原始组不承担这项额外缓存重建。

| 接收端数 | 候选列表失效频率 | 原始嵌套遍历 | 缓存展开遍历 | 变化 |
| ---: | --- | ---: | ---: | ---: |
| 64 | 不失效 | 1.244 µs | 1.209 µs | -2.8% |
| 512 | 不失效 | 10.826 µs | 10.097 µs | -6.7% |
| 512 | 每 32 次 | 10.843 µs | 11.446 µs | +5.6% |
| 512 | 每次 | 10.840 µs | 47.024 µs | +333.8% |

简化模型中，稳定的 512 端点网络一次发送节省约 0.73 µs；重建会吞掉收益。这个模型的容器、分配、目标实现和 CPU 状态与真实游戏不同；其中 512 个端点也不表示用户实例存在这样的网络。数字不能外推成 MSPT 收益。

## 决定与后续

当前原型只有简化模型，且稳定网络的绝对收益很小、重建成本明显，暂不把它安装进整合包。下一步比直接移植该方案更有价值的是在真实网络上计数：每网络的端点分布、每 Tick 发送次数、拓扑失效频率、模拟调用次数与耗时，再决定是否值得实现能正确处理所有生命周期的候选。如果目标是查找更大的算法热点，也应继续研究重复模拟和跨机器调用的成本，但不得无条件复用模拟结果。

## 复现

JDK 17 下设置 `JAVA_HOME`，运行 `python tools/run-transfer-topology-simulation.py`。默认读取 `build/reference/mekanism-50978fc-source.zip`，脚本验证其 SHA-256，再提取仅用于编译的三个 Mekanism 类；可用 `--source-zip` 指定该提交的同一归档。模型与脚本分别为 `tools/experiments/TransferTopologySimulation.java` 和 `tools/run-transfer-topology-simulation.py`；结果在 `build/reports/mekanism-transfer-simulation/`。
